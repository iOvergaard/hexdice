# Playtest 18-11-2026: offline mode

**Branch:** `feat/offline`, off main `64a22a6`. No game code changed: a service worker, its registration, the build plugin that writes it, and their tests. No new dependencies.

## What's new

- `src/offline/service-worker.js`: the worker. On install it caches every file of its own build in `hexdice-<build id>`. On activate it deletes every other `hexdice-*` cache and takes control of open pages.
- `scripts/offline.ts`: a Vite plugin (`apply: 'build'`) that runs after the build, reads `dist/`, and writes `dist/sw.js`: the worker with the build's file list and cache name prepended. The build id is a content hash of those files, so rebuilding the same code gives the same `sw.js` and updates nobody. The list skips `sw.js` itself, `og-image.png` (link previews only) and source maps. Today that is 10 files, about 400 kB before compression.
- `src/offline/register.ts`, called from `src/main.ts` only when `import.meta.env.PROD`: registers `./sw.js` after `load`. Dev servers and the existing Playwright suites never see a worker.
- `tsconfig.json`: `allowImportingTsExtensions`, so `vite.config.ts` can import `./scripts/offline.ts` with its extension. Without the extension, Vite warns on every run that its future native config loader will need it. Safe with `noEmit`.
- The Pages workflow needs no change: `sw.js` is part of `dist/`, and `npm run e2e` in CI picks up the new spec.

## Which update mechanism, and why

**Updates on next load, with no prompt.**

- **Pages come from the network first.** Online, every visit fetches the page from GitHub Pages, so returning players get the deployed build on their first visit after a deploy. The worker revalidates (`cache: 'no-cache'`, a cheap 304 when nothing changed). Without that, Pages' ten-minute `max-age` could serve a cached page that names assets the deploy has already removed.
- **Offline, or when the connection stalls for 4 seconds,** the page and its assets come from the newest complete build the worker holds. Every cache holds exactly one build, so a page never mixes builds.
- **The new worker takes over at once** (`skipWaiting` and `clients.claim`) and deletes the old cache. So the next offline session already runs the new build, even on a phone that never really closes the home-screen app. The browser checks `sw.js` against the network on every visit, bypassing the HTTP cache, and each deploy changes its bytes.
- **No "new version, reload" prompt.** Online players already get the new build on load, so a prompt would only interrupt a game in progress. It would also need UI copy and a DOM element in `src/ui`, which other branches are changing. Swapping caches under a running page is safe here because the game loads as one JS file and one CSS file at start.
- **Never stuck on a stale build:** the online path always asks the server first, and a broken worker can always be replaced, because the browser fetches `sw.js` from the network.

## Notes for later

- To remove offline mode one day, don't just delete `sw.js`. If the update check gets a 404, browsers keep the worker they have. Ship a `sw.js` that unregisters itself and clears its caches instead.
- Safari: WebKit's 2020 announcement says Safari deletes a site's script-writable storage (this cache, and the saves in localStorage) after seven days of Safari use without a visit, and that home-screen web apps are exempt ([webkit.org](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). Not tested here.
- A first visit asks for each file twice: once for the page, then again for the worker's cache. The second request is a revalidation, so it is a 304 with no body wherever the HTTP cache already has the file.
